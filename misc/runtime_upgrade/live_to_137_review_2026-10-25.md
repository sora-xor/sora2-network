## Finding

**P2 — the build verifier could attest stale Wasm against fresh source (resolved).** In the [archived original runner](../../runtime-rehearsal-async-staking-2026-10-25/validation/attempts/before-build-environment-fix-20261025T130526Z/run-build-verification.py#L9), environment sanitization removed `SKIP_WASM_BUILD` but preserved `SKIP_FRAMENODE_RUNTIME_WASM_BUILD` and `DOCS_RS`. The SDK builder treats the presence of either variable as an instruction to skip compilation and leaves an existing build artifact in place. With a warm target directory, the original lines 39–48 could subsequently validate the old generated manifest, copy the old Wasm, and emit a passing attestation containing the newly captured source fingerprint. A source behavior change without a spec-version change could therefore escape the intended source-to-binary binding.

Executing the actual environment-construction statements with synthetic values reproduced both leaked flags. The skip and artifact-reuse paths were verified in source; a full fault-injected release run was not performed. This finding does **not** establish that the current candidate is stale. Clear or reject every relevant skip control and explicitly control or record nested Wasm build flags, Cargo arguments, and toolchain selection. Add a regression covering an existing artifact plus a skip request, then regenerate the build attestation and dependent release verification as appropriate. Preserve the warm Cargo target directory.

The [environment witness](../../runtime-rehearsal-async-staking-2026-10-25/validation/live-review/build-environment-witness.json) records the original tested inputs and script hashes. The subsequent fix clears the bypasses, pins build controls, requires recreated exports, and independently binds the evidence. Twenty new regressions and six proof-mutation checks passed; the rebuilt candidate is byte-identical. This finding is closed; its description above records the original defect.

## Compatibility and governance implications

This is not a behavior-neutral dependency update. Governance release notes need to state the new-era slashing differences explicitly: liabilities are calculated per validator and offence era rather than the old cross-validator nominator span maximum; async reports retain the first reporter and reward a fraction of the incremental slash rather than the historical span-halving formula. Historical commitments retain their original policy, and the additional era of nonzero slash deferral is preserved.

Existing Staking call/event/error encodings and storage queries are preserved. The reviewed additions include seven staking calls for async slash cancellation/application, configuration, pruning, commission/self-stake policy, and inactivity chilling; new staking state/events/errors/constants; and the local `StakingAsyncBridge` pallet. Identity adds registrar removal. These are explicit additions, not silently ignored metadata differences.

Clients must refresh metadata and sign using transaction version **133** after activation. `System.CodeUpdated` gains a hash field and changes its event encoding. `Offences.Offence` renames `timeslot` to `slot` without changing field encoding. Existing runtime API versions and host function signatures are unchanged. Old pre-signed transactions and clients pinned to old event metadata must not be assumed compatible across activation.

All 2,061 pending bridge preimages were recovered in the recorded inventory. Twelve decode identically under live and candidate runtimes; 2,049 already fail under both. No new rejection or newly enabled old payload was found. Their maximum payload is 278 bytes versus the 16,384-byte cap. The cancellation review is unsigned preparation for the obsolete entries, not executed cleanup. The loader bounds runtime allocation, not the host's backend read or trie-proof size.

## Verification reviewed and refreshed

Fresh checks in this review confirm the live runtime hash, unchanged candidate source, metadata comparison with zero unreviewed changes, and independent offline reproduction of the two retained bridge inventories. The bridge recheck is not a new live pending-operation scan. The metadata comparison still deliberately reports universal raw SCALE compatibility as false because of the reviewed SDK changes.

The previous candidate-bound verification records **943 passing Rust test executions**, three pre-existing ignored tests, all three full Clippy configurations, and **24 passing production Wasm rehearsal stages**. The staking witness covers all 21,509 captured keys; 21,507 existing keys are byte-identical, with expected storage-version and authorship-point changes. All 4,733 values across the affected public query prefixes preserve JSON and SCALE roundtrips. The dependency results cover 11 maintained Cargo locks, five harness locks, and eight npm graphs. Those suites were reviewed, not rerun or relabeled as new executions in this review.

Rehearsals use pinned/scoped public state, synthetic fixtures, and disclosed outer-signature mocking; they do not establish whole-chain `try_state`, an independent state-root/finality proof, or mixed-version validator consensus. Added compatibility weights are conservative accounting, not newly generated hardware benchmarks. Activation bounds were satisfied by the pinned state and must remain satisfied at the actual upgrade: at most 256 nominators and one exposure page per validator, 1,200 validator records per era, and 512 KiB per frozen slash value. Current runtime identity alone does not refresh those state-dependent facts.

Before publication, final Linux images still need binary/runtime provenance, loader and launch-argument checks, copied-database restart, keystore/OCW persistence, network synchronization, and image-package scanning. Per the user's rollout sequence, operators upgrade after immutable image publication and confirm readiness before governance runtime activation. No operator access is required to prepare the image. No production transaction, image publication, or activation occurred in this review.
